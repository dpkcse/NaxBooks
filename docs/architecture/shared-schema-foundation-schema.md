# Shared-schema foundation target design — Step 5 proposal only

**Not implemented.** The primary shared schema is canonical; `tenant_id` comes only from trusted `CurrentTenant`, is guarded from request input, and is assigned by an approved server-side action. All business FKs use `restrictOnDelete`; archival/status transitions replace hard deletion. MySQL cannot express “child tenant equals parent company tenant” with independent FKs alone, so services, policies, scoped binding, and composite validation must assert every chain.

## Default and consistency rules
A normal MySQL unique index cannot enforce one `is_default=true` or one `is_base=true` while allowing many false rows. Step 5 must first run repair queries, then use transactional service methods with `SELECT ... FOR UPDATE` to clear/select defaults; optionally assess generated-column unique indexes only after MariaDB 10.4/MySQL 8 rehearsal. Assert unique company codes, branch codes, currency codes, access assignments, and company/branch tenant equality before adding strict constraints.

## Foreign-key and performance policy
Use same-schema FKs listed above, no cascade deletion of business/audit data, and `nullOnDelete` only for intentionally retained audit actor/company references. Use unsigned bigint FK types and named indexes within 64-character MySQL identifier limits. Required tenant-leading indexes are listed in the table; they are compatible with MariaDB 10.4 and MySQL 8 for the short code/status/key columns. Do not add partitioning/sharding; measure cardinality and query plans after production-like data exists.
